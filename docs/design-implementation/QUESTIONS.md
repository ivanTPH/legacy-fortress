# V4 design questions requiring product or service decisions

1. **Multiple roles per person:** the existing canonical contact and invitation model exposes one primary role. Should V4 show additional linked relationships as read-only labels, or is a separately approved data-model change planned?
2. **Revoke Undo:** V4 shows a Toast Undo after immediate revocation. A safe, audited inverse grant operation is not established. Confirm whether to omit Undo until a dedicated service exists.
3. **Request-specific record selection:** current verification requests identify a requester, type and notes, but do not reliably carry canonical requested record IDs. Confirm how “Approve and choose records” should preselect records. Approval itself will continue to leave sharing unchanged.
4. **Form required fields:** V4 suggests type-specific required fields. Existing field dictionaries and backend validation remain authoritative until the owner approves individual changes to required status.
5. **Audit history:** V4 asks for the latest three access events and a full-history link. Confirm an authorised, contact-scoped audit API before surfacing events or a link.

## V5 decisions and implementation gates

**Approved for planning:** Use V5 as the current visual reference, retain V4 history, and deliver in owner-reviewed stages: Personal Vault mobile; People & Access/mobile forms; Platform Admin mobile; Partner Portal mobile; then desktop consistency. Keep current authentication, roles, routes, grants, RLS and deployment controls. None of the questions below is permission to add backend capability.

6. **Resolved — security-domain switching:** the owner mandates separate Personal Vault, Platform Administration and Partner Portal entry points. Ordinary users must not switch between them. Customer switching is limited to Personal and authorised linked Vault contexts. A future TEST-only launcher for the authenticated master owner may navigate between separately authenticated environments; it must not impersonate, elevate or expose private Vault records. It requires server enforcement and audit and is outside Stage 1. Proposed future hosts are `app.mylegacyfortress.com`, `admin.mylegacyfortress.com` and `partners.mylegacyfortress.com`, not configured destinations.
7. **Three-interface consolidation:** Should existing Enterprise Operations and Platform Probate Review routes remain as compatible entry points if their navigation is later grouped under Platform Admin? Specify role mapping, redirects and migration acceptance before any change.
8. **Approved direction, implementation pending — separate sign-in:** proposed URLs are `/admin/sign-in` and `/partner/sign-in`, alongside existing customer `/sign-in`. Confirm provider, recovery, session isolation, protected master-owner role assignment, distinct privileged and Vault identities, last-master-admin and protected recovery behaviour, and migration/rollback design before implementation. Roles must attach to verified account IDs, never names or emails. Existing shared authentication stays in place during Stage 1.
9. **Partner Portal:** Confirm the approved public route/label and which V5 Team, Registration links, Reports and Activity views can map to existing `/enterprise/*` services. Unbacked prototype actions must not appear functional.
10. **Customer workspace labels:** Confirm “Personal” and “Linked to you” labels for existing authorised customer contexts. “Work” and “Legacy Fortress staff” are excluded from the ordinary customer switcher by decision 6.
11. **Mobile form presentation:** V5 specifies full-screen Add/Edit modals without the customer tab bar. Confirm whether existing deep links and back behavior should stay on their current URLs while adopting that presentation.
12. **Admin action reasons:** Identify any V5 risky actions whose current canonical service does not store an audited reason. Do not add an unaudited field or claim an action is reversible.

## Linked people V5.2 — PR 1 decisions before later stages

13. **Role vocabulary:** Confirm the role lists and contextual headings in `LINKED_PEOPLE.md`, especially firms versus individual people and the meaning of “Other”. PR 1 stores a validated role label without granting access.
14. **Existing relationships:** `record_contacts` and `contact_links` already hold legacy links; the latter enforces one contact per source. Confirm the provenance and deduplication rules for a later additive backfill into `record_links`. PR 1 leaves both tables and all existing readers unchanged.
15. **Document provenance for legacy records:** Canonical `documents` belong to `assets`, while older `records` use `attachments`. PR 1 permits manual links on either parent but confines extraction suggestions to canonical asset documents. Confirm how evidence from a legacy attachment should be represented before PR 4.
16. **Invitation association:** Existing `contact_invitations` are primarily contact/role scoped and have an active email/role uniqueness rule. Confirm whether one invitation should be shown across every record linked to that person, or whether later invitation events must reference a particular `record_link`. No invitation sender or access grant changes are in PR 1.
17. **Expiry and retention:** Confirm the intended resend interval, seven-day delivery handling, thirty-day expiry, and whether deleting a contact or source document must be blocked while a relationship/audit source exists. PR 1 adds statuses but changes no timers or retention behaviour.

## Linked access security blocker (27 October 2026)

18. **Legacy association widens an active grant:** A rollback-only synthetic local test showed that `linked_grant_allows_asset` treats `contact_links` as access and `linked_grant_allows_record` treats `record_contacts` as access when the linked contact already has an active, identity-qualified `account_access_grants` row with empty explicit scope. Both paths also allow the related document/storage reads. The new `record_links` table does not participate in those functions, and changing its role did not widen the grant. Revoking the grant stopped subsequent reads. Approve a **separate security remediation** of the legacy grant-scope/RLS functions, with compatibility review for existing intentional shares, before any new permission integration or legacy backfill. Do not use legacy contact associations as a substitute for explicit Give access.
