## Boundaries and status

- Baseline for this handoff integration: remote staging `0557f28cf7312b40650e3c8e674f9dde9c36c97b`. V4 mobile and workspace-header corrections are in that commit. The retained V4 supplement was committed separately at `f327ae2`; V5 corrects it on the points enumerated in `MOBILE_V4.1.md`.
- The existing application supplies customer, contact, invitation, grant, identity, admin and enterprise functions. This handoff records **new visual requirements**; it does not assert that V5 screens are already implemented or accepted. See [`V4_V5_IMPLEMENTATION_GAPS.md`](V4_V5_IMPLEMENTATION_GAPS.md).
- Preserve Supabase Auth, RLS, authorised record-level counts and data, invitation lifecycle, identity assurance separate from access grants, linked-Fortress isolation, estate/probate restrictions, audit and organisation boundaries. Never substitute prototype names, figures or fixtures for live data.
- The owner has resolved the V5 conflict about cross-domain switching as described below. Proposed navigation consolidation, new sign-in/session implementation, route/role migration and new audited actions remain separately gated; see [`QUESTIONS.md`](QUESTIONS.md).
- **Owner decision, 17 Oct 2026:** Personal Vault, Platform Administration and Partner Portal are three separate security entry points with appropriate session boundaries, server-enforced RBAC, tenant isolation and RLS. Ordinary users must not navigate between these domains with a workspace switcher. The Stage 1 customer selector shows only Personal Vault and authorised linked Vault contexts. A future TEST-only owner launcher may navigate between independently authenticated test environments, but must never impersonate users or grant privileges. It requires authenticated identity and protected master-role proof, server enforcement and audit; it is disabled in production by default. Stage 1 does not implement it.
- The founding owner's privileged Platform Admin identity must be separate from an ordinary Personal Vault identity. Appointments and delegated roles must be assigned to verified account IDs, never hardcoded names or email addresses. Platform administrators have no default access to private Vault records. Preserve the last-master-admin safeguard and define protected account recovery before any security migration.
- Proposed future production hosts are `app.mylegacyfortress.com`, `admin.mylegacyfortress.com` and `partners.mylegacyfortress.com`; none is an implemented or configured destination. Current authentication and navigation retain legacy cross-domain capabilities outside the Stage 1 customer shell. Removing those capabilities requires the separately approved security migration described below.
- Proposed login URLs: existing customer `/sign-in`; future staff `/admin/sign-in`; future partner `/partner/sign-in`. The latter two are **design proposals, not implemented routes**. Existing `/admin/*` and `/enterprise/*` operations continue under current authentication until a separately approved security migration establishes distinct sign-in/session handling, protected master-owner assignment, last-master/self-removal safeguards, and tested server enforcement.
- Deliver in reviewed stages per [`V4_V5_DELIVERY_PLAN.md`](V4_V5_DELIVERY_PLAN.md). No V5 application code, hosted configuration or database change is included in this documentation integration.
