# V4 to V5 implementation gaps

Baseline: deployed staging `0557f28` and the V5 package indexed in [`DESIGN_SOURCE_OF_TRUTH.md`](DESIGN_SOURCE_OF_TRUTH.md). This is a targeted file-level map, **not a claim of visual acceptance**. Confirm each gap with actual browser states in its implementation stage.

| Priority / surface | Existing implementation | V5 delta or acceptance gap | Boundary / focused proof |
| --- | --- | --- | --- |
| 1. Personal Vault mobile | Customer shell, fixed four-tab bar and role-filtered `WorkspaceSwitcher` exist in `app/(app)/layout.tsx`, `components/navigation/WorkspaceSwitcher.tsx` and `app/globals.css`. V4 mobile overflow corrections are in `0557f28`. | `MOBILE_V4.1.md` specifies a 52px root/pushed header, docked bar with scroll region ending above it, compact full-width summary, Records/People/Actions KPIs, responsive two-column Vault, distinct drawer and overlay workspace sheet. Existing fixed-bar padding and menu composition need measured comparison at all four V5 sizes. | Keep existing authorised destinations and counts. Prove no horizontal overflow, bottom overlap, focus loss or role leakage at 390×844, 320×568, 402×874 and 390 at 125% text; desktop remains stable. |
| 2. People & Access | `/people-access` already combines People, Requests and Sharing; contact, invitation, identity and saved grant services exist. Shared record controls already separate required and optional fields. | V5 specifies pushed mobile person page, clear Connected / Identity verified / Access granted rows, bounded Give/Edit Access sheet, explicit record selection, safe-area actions and consistent mobile form chrome. These states have not been accepted against the new reference. | Invitation or verification must not grant records. Exercise owner edit/save/reload/revoke, linked assigned-only and wrong-user denial with synthetic accounts; preserve existing service semantics. |
| 3. Platform Admin mobile | `/admin/*` and `AdminWorkspaceShell.tsx` have a responsive drawer and existing capability-filtered navigation. | `CONSISTENCY.md` and `Admin and Partner Mobile.dc.html` specify a 56px header, role-specific mobile tabs, readable two-line rows, full-screen panels and safe-area actions. Current shell needs a focused 390px comparison. | Navigation must follow server capabilities; no customer vault detail, role or probate permission change. |
| 4. Partner Portal mobile | `/enterprise/*` and `components/enterprise/*` provide organisation functions. | The V5 Partner Portal has distinct visual navigation, registration/login states, team/seats, invitations, reports, licence and activity views. Existing routes/functions must be mapped before implementing any missing interface; no new auth or data model is authorised. | Verify organisation scope, seat/invitation lifecycle and admin isolation with synthetic identities. Missing backend-backed views stay explicit rather than becoming dummy controls. |
| 5. Desktop consistency | Shared tokens, Material Symbols, forms and V4 People presentation exist. | Apply V5 `CONSISTENCY.md` copy/icon/state rules and `ADMIN_PARTNER.md` page/panel patterns to the relevant desktop screens after mobile stages are accepted. Any Admin/Enterprise/Probate consolidation or separate staff sign-in is a gated architecture decision. | Use shared components; preserve existing routes, permissions and audit. Check 1440px desktop only for changed surfaces. |

Supporting design history remains in [`V4_CANONICAL.md`](V4_CANONICAL.md) and the [V4 mobile supplement](V4_MOBILE_SUPPLEMENT.md). Its floating-bar and Debts KPI guidance is superseded by V5 mobile V4.1; do not silently copy the older screen into the application.
